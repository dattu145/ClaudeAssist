# Research: Claude Code CLI/SDK Integration

Environment checked on this machine (2026-09-09, Windows 11, `claude --version` = 2.1.266).
This is the authoritative source for how ClaudeOps's `ClaudeCodeAdapter` talks to Claude Code.
Re-verify against `claude --help` when the installed version changes — flags evolve.

## CORRECTION (page8, 2026-09-09): `--bg` is not the dispatch primitive

The original version of this doc assumed `claude --bg --session-id <uuid> -p
"<instruction>" --output-format stream-json` would both start a
controller-managed session *and* be resumable via `-p --resume` for
subsequent instructions. **Both assumptions were wrong**, verified against
the real CLI (v2.1.266):

1. `--bg` and `--print`/`-p` are mutually exclusive. Real error: `--bg and
   --print conflict: --print never starts the interactive session that
   \`claude agents\` attaches to, so the job would be unattachable.` `--bg`
   starts a detached **interactive** session (the kind you open with `claude
   attach`), not a headless one-shot dispatch.
2. `--session-id` is **ignored** when combined with `--bg` (real warning:
   `--bg manages the session id; ignoring --session-id`) — the id is
   generated by `--bg` itself.
3. A session currently running as a `--bg` job **cannot** be dispatched to
   via `-p --resume <id>` — real error: `Session <id> is running as a
   background session (<short-id>). Run \`claude attach <short-id>\` to open
   it, or \`claude stop <short-id>\` first to resume it here.`

**Consequence for the adapter design**: `--bg` is not used at all for
ClaudeOps-managed sessions. The chosen design (below) uses only `-p
--session-id`/`-p --resume` — short-lived, non-backgrounded processes for
every dispatch — which sidesteps this conflict entirely. `--bg` remains
useful only for a *possible future* "let this run unattended and let me
`attach` to watch it live" feature, explicitly out of scope for Phase 1.

## Mechanisms available (no screen scraping needed)

### 1. `claude agents --json` — read-only discovery of running CLI processes
- `claude agents --json [--all] [--cwd <path>]` lists active (and, with
  `--all`, completed) background **and interactive** `claude` processes as a
  JSON array. No TTY required. Real verified shape (2026-09-09):
  ```json
  [
    { "pid": 19700, "cwd": "C:\\...", "kind": "interactive",
      "startedAt": 1788934467424, "sessionId": "<uuid>", "name": "...",
      "status": "busy" },
    { "pid": 37348, "id": "a2a127a8", "cwd": "C:\\...", "kind": "background",
      "startedAt": 1788946916384, "sessionId": "a2a127a8-1324-...",
      "name": "page8-probe", "status": "idle", "state": "done" }
  ]
  ```
  `sessionId` is the real Claude conversation UUID. `kind: "background"`
  entries additionally carry a short `id` (used by `attach`/`logs`/`stop`) —
  observed to be literally the first UUID segment of `sessionId`, but treat
  that as an implementation detail, not a contract. `status` (`"busy"` |
  `"idle"`) reflects whether the process is actively generating; `state`
  (background jobs only, e.g. `"done"`) reflects the background job's own
  lifecycle. This only reports **currently-running processes** — a
  resumable conversation with no active process (the common case between
  dispatches under the chosen design) does not appear here. It is a
  discovery/reconciliation signal for sessions ClaudeOps did *not* itself
  just dispatch to, not a general session-history query.
- `claude attach <id>` opens a background session's terminal (interactive;
  not for the controller to call programmatically, but useful for a "open in
  terminal" mobile action that shells out on the controller host).
- `claude logs <id>` prints a background session's recent terminal output as
  **raw ANSI-escaped TUI text** (verified: not JSON, not clean text — real
  sample was full of `\x1b[K` cursor-control sequences). Confirms this must
  stay a last-resort human-facing fallback, never parsed programmatically.
- `claude stop|kill <id>` stops a `--bg` session (conversation preserved,
  resumable afterward). Not part of the chosen per-instruction dispatch flow
  since that flow never uses `--bg`.
- `claude rm <id>` deletes a background session's record (and worktree, when
  safe).
- `claude respawn [id|--all]` restarts a background session on the current
  CC version — relevant only if a future feature uses `--bg`.

### 2. Non-interactive dispatch — the core primitive for "send instruction"
- `-p/--print` runs one turn and exits. Skips the trust dialog.
- `--output-format stream-json` **requires `--verbose`** when combined with
  `--print` — verified real error without it: `Error: When using --print,
  --output-format=stream-json requires --verbose`. Every dispatch command
  must include both flags together.
- Real stream-json line shapes, captured 2026-09-09 against v2.1.266
  (`claude -p "..." --output-format stream-json --verbose --permission-mode
  dontAsk`):
  - `{"type":"system","subtype":"init","session_id":"<uuid>","cwd":...,
    "model":...,"permissionMode":...,  ...}` — first substantive line; the
    authoritative source for the real session id (confirms/replaces the
    requested `--session-id`).
  - `{"type":"system","subtype":"hook_started"|"hook_response", ...}` —
    session-start hook lifecycle noise; ignore for adapter purposes.
  - `{"type":"assistant","message":{"content":[{"type":"text","text":"..."}],
    ...},"session_id":...}` — assistant turns; concatenate `text` blocks
    across these lines for streaming output.
  - `{"type":"rate_limit_event", ...}` — ignore for adapter purposes.
  - Final line: `{"type":"result","subtype":"success"|..., "is_error":bool,
    "result":"<final text>","session_id":...,"permission_denials":[...],
    "total_cost_usd":...,"num_turns":...,"terminal_reason":"completed"|...}`
    — the authoritative outcome. `permission_denials` (non-empty when a
    tool call was auto-denied under the active permission mode) is the
    signal used to map to `WAITING_FOR_PERMISSION` (see "Chosen adapter
    design" below).
  - Malformed/unparseable lines are logged and skipped, never thrown (per
    RISKS.md).
- `--include-partial-messages` streams partial message chunks (finer-grained
  progress) — not used in Phase 1's adapter (one result per dispatch is
  sufficient); a lever for future finer-grained `SESSION_TASK_PROGRESS`.
- `--json-schema <schema>` constrains structured output — not used in Phase
  1; a lever for a future more-structured outcome format if free-text
  parsing of `result` ever proves insufficient.

### 3. Session identity and resumption
- `--session-id <uuid>` sets a specific session id at start for a plain
  (non-`--bg`) `-p` invocation — verified working. (It is silently ignored
  when combined with `--bg`, see the correction above — another reason
  `--bg` is not used for managed sessions.)
- `-r/--resume [session-id]` resumes a conversation by id — verified working
  against a session that was previously stopped from `--bg`; expected to
  work identically against a plain `-p --session-id`-started conversation
  since both are just persisted conversation history on disk.
- `-c/--continue` resumes the most recent conversation in the current directory (fragile —
  depends on cwd; prefer `--resume <id>` once an id is known).
- `--fork-session` forks into a new session id on resume — useful for a future "branch this
  task" feature, out of scope for Phase 1.
- `--no-session-persistence` (print mode only) explicitly opts OUT of resumability — the
  adapter must never pass this for managed sessions.

### 4. Permissions (maps directly to the spec's READ/EXECUTE/WRITE/DESTRUCTIVE requirement)
- `--permission-mode <acceptEdits|auto|bypassPermissions|manual|dontAsk|plan>` — Phase 1
  default MUST NOT be `bypassPermissions`. Default to `plan` or `manual`/`auto` depending on
  operation risk class (see SECURITY.md).
- `--permission-prompts <host|none>` — controls who answers a prompt in print mode. `none`
  auto-denies anything requiring approval; useful as a safe default for fully unattended
  dispatch, with `host` reserved for sessions where a human is actively watching via mobile.
- `--allowedTools` / `--disallowedTools` — per-session tool allowlist, another lever for
  the DESTRUCTIVE-operation gating the spec requires.
- `--restricted` — strips Bash/PowerShell/code-exec tools and WebFetch entirely; a strong
  default for sessions dispatched from voice/mobile with no human watching the terminal.
- `--dangerously-skip-permissions` — explicitly forbidden as a default per the spec; the
  adapter interface should not expose a code path that sets this without an explicit,
  logged, user-initiated override.

### 5. Scripting/config surface useful to the controller
- `--settings <file-or-json>`, `--mcp-config`, `--add-dir`, `--model`, `--effort`,
  `-n/--name` — all settable per dispatched session; the controller can pass these through
  from `StartSessionInput` without needing its own equivalents.
- `claude doctor` — health/diagnostic check of the CC installation itself; wire into the
  controller's own `/health` endpoint as one input signal.

## Platform note: invoking the CLI from Node on Windows

On Windows, the npm-installed `claude` command is a `claude.cmd` shim (in
addition to a real `claude` binary launcher). Two things were verified
empirically (2026-09-09, v2.1.266), not assumed:

1. `child_process.execFile("claude", ...)` without a shell fails with
   `ENOENT` — `execFile` only resolves real executables, not `.cmd`
   wrappers. Use `child_process.exec("claude ...")` (shell) instead — fine
   when the command string has no interpolated untrusted input, as in
   `apps/controller/src/health.ts`'s `defaultCheckClaudeCli`.
2. `child_process.spawn("claude.cmd", args)` **without** `shell: true`
   throws synchronously with `EINVAL` — Node deliberately disallows spawning
   `.bat`/`.cmd` files without a shell (a hardening fix for
   CVE-2024-27980). This matters for `apps/controller/src/adapters/
   claude-code/cli.ts` (page8), where `args` includes arbitrary
   user-supplied instruction text, so shell-string injection risk needed
   real verification, not assumption: `spawn(cmd, argsArray, { shell: true
   })` was tested with an argument containing `"` and `&`
   (`hello" & echo INJECTED > injected.txt & echo "`) and confirmed the
   payload was passed through as one literal argument with no command
   execution — Node quotes each array element individually for cmd.exe even
   under `shell: true`. The DEP0190 deprecation warning still fires (Node's
   blanket caution, not a confirmed vulnerability in this case) — documented
   here as a known, intentional, tested tradeoff, not an oversight. POSIX
   needs neither the shell nor this concern: no `.cmd` wrapper exists there,
   the real `claude` file's shebang line is exec'd directly.

## What this rules out

- No need for terminal screenshotting, keystroke injection, or Playwright-driven terminal
  automation for **managed** sessions (started by ClaudeOps). `--bg` + `-p --output-format
  stream-json` + `claude agents --json` covers start, dispatch, discover, and monitor.
- **Attaching to a pre-existing *interactive* session the user started manually outside
  ClaudeOps** (e.g. a `claude` REPL running in a terminal the user opened themselves) has no
  supported programmatic attach point beyond `claude attach <id>` (itself interactive, and
  only for sessions `--bg` created) and `claude agents --json` (read-only status/discovery,
  works for both interactive and background sessions per `claude agents --help`). There is
  no documented mechanism to inject an instruction into an already-running interactive REPL
  session from outside. **Limitation, not a workaround target**: Phase 1 supports (a) full
  lifecycle control of sessions ClaudeOps itself starts and dispatches to (plain resumable
  `-p --session-id`/`-p --resume` conversations, see "Chosen adapter design" below — not
  `--bg`), and (b) read-only discovery/status of any session `claude agents --json` reports,
  including ones the user started by hand. Sending instructions to a manually-started
  interactive session is out of scope until Claude Code exposes a supported IPC/attach
  mechanism for that case — do not build a terminal-automation workaround for it.

## Chosen adapter design (`ClaudeCodeAdapter`), revised post-page8 verification

Every ClaudeOps-managed session is a **plain resumable conversation**, never
a `--bg` job. There is no persistent OS process for a session between
dispatches — only a short-lived child process while a dispatch is actively
running. This is a real simplification: `stopSession`/`resumeSession` don't
need `claude stop`/`claude --resume` shelled out at all; they mostly become
local bookkeeping (see below).

- **First dispatch to a session** (no `claudeSessionId` recorded yet):
  `claude -p "<instruction>" --session-id <uuid> --output-format stream-json
  --verbose --permission-mode <mode> [--restricted]`, spawned with `cwd` set
  to the project path. The real session id is read back from the
  `system`/`init` line, not assumed to equal the requested `--session-id`
  (though it is expected to match).
- **Subsequent dispatches**: `claude -p "<instruction>" --resume
  <claudeSessionId> --output-format stream-json --verbose --permission-mode
  <mode> [--restricted]`, same short-lived-process model.
- **Outcome mapping** from the final `result` line:
  - `permission_denials.length > 0` -> `InstructionResult.status =
    "waiting_for_permission"` (a tool call was auto-denied under the active
    permission mode; a human needs to grant it before that work can
    proceed). This is the only way `WAITING_FOR_PERMISSION` is reachable
    through this non-interactive flow.
  - else `is_error === true` -> `"failed"`.
  - else -> `"completed"`.
  - **`WAITING_FOR_INPUT` is not reachable via this dispatch path.** A
    one-shot `-p` process either finishes or errors; it never pauses
    mid-turn to ask the human a free-text question the way an interactive
    REPL can. This is a documented Phase 1 limitation, consistent with the
    existing "no attach to manually-started interactive sessions" limitation
    below — both stem from the same root cause (only interactive sessions
    can genuinely "wait", and Phase 1's dispatch model is non-interactive by
    design, per ADR-003).
- **Discover** (read-only, for sessions ClaudeOps didn't just dispatch to):
  poll `claude agents --json --all` on a configurable interval (spec forbids
  uncontrolled polling loops; this one is bounded and interval-configurable)
  plus an on-demand call during controller startup reconciliation. Returns
  process-level info (pid, cwd, sessionId, kind, status) with **no
  `projectId`** — matching a discovered session to a registered `Project` by
  `cwd` is the Session Registry's job (page9), not the adapter's; the
  adapter has no knowledge of the Project Registry.
- **Status**: derived from the last dispatch's outcome (tracked locally per
  session) plus, for discovery purposes, `claude agents --json`'s `status`/
  `state` fields — never from parsing rendered terminal text (`claude logs`
  stays a human-facing fallback only, confirmed unparseable — see above).
- **Stop**: if a dispatch is currently in-flight for the session (the
  adapter tracks its own spawned child processes), kill that child process.
  Otherwise a no-op at the CLI level — there is no persistent process to
  stop between dispatches under this model.
- **Resume**: a no-op at the CLI level — the next `sendInstruction` call
  naturally resumes via `--resume <claudeSessionId>`; nothing needs to be
  "done" in advance. `resumeSession` exists on the port primarily for the
  domain-level state transition (`STOPPED`/`FAILED` -> `STARTING` ->
  `WORKING`), not because the real adapter has CLI work to do.

This design fulfills the spec's "DO NOT build the core system around fragile
screen scraping" requirement using only documented, verified CLI behavior —
and, per the spec's own instruction ("do not blindly use the [conceptual]
API if the official interfaces suggest a better design"), corrects the
original `--bg`-based assumption after real testing proved it unworkable for
a resumable multi-instruction session model.
