# Risks and Technical Constraints

| Risk | Impact | Mitigation |
|---|---|---|
| `claude` CLI flags change between versions | Adapter breaks silently | Version check on startup (`claude --version`/`doctor`); adapter tests run against the real CLI in CI where possible; research doc re-verified on upgrade |
| No supported way to attach to a manually-started interactive session | Voice/mobile can't send instructions into sessions the user opened by hand | Documented limitation (ADR-003); Phase 1 scope is managed sessions + read-only discovery of others |
| Terminal discovery is not reliably cross-platform | `Terminal` entity often null/best-effort | Modeled as optional metadata, never load-bearing for core state (architecture/session-model.md) |
| stream-json parsing edge cases (partial lines, malformed JSON, tool-use nesting) | Missed/duplicate events, incorrect state | Buffered line parsing with tests against captured real CLI output; malformed lines logged, not thrown |
| SQLite single-writer under bursty event volume | Write contention on long-running heavy sessions | Batch event writes; WAL mode; revisit only if profiling shows an issue |
| Windows-first dev environment vs. eventual macOS/Linux use | `ProcessDiscoveryService` must not hard-code one OS | Platform abstraction with per-OS implementations from the start (spec requirement) |
| `ProcessDiscoveryService`'s POSIX implementation is genuinely unverified | `ps` parsing could be subtly wrong on real macOS/Linux (BSD vs. GNU `ps` flag differences, etc.) | Windows implementation verified against this machine's real process list (page15); POSIX parsing only unit-tested against representative fixture output — whoever first runs the controller on macOS/Linux should treat it as "verify before trusting," not assumed-working |
| Mobile app on a network without reachable controller (no tunnel yet) | Dashboard unusable off-LAN | Explicitly out of scope for Phase 1; document as a known limitation, not solved with a quick tunnel hack |
| Android background/mic restrictions | Future voice feature could over-promise | research/android-background.md stub flags this before any implementation starts |
| Scope creep into voice/WhatsApp/Bordio during Phase 1 | Phase 1 never ships | Hard boundary enforced by MASTER_PLAN.md page sequence; those integrations are separate, later pages |
| Stale cross-package `dist/` output masking source changes | A package edit doesn't take effect for consumers until rebuilt, causing tests to pass/fail against old code (hit during page4) | Root `npm test` runs `tsc -b` first (`pretest` script); `npm run typecheck` before `npm test` whenever a shared package changed |
| `child_process.execFile` can't find Windows `.cmd` shims (e.g. `claude.cmd`) | Silent `ENOENT`, health checks report false negatives | Use `exec` (shell) for CLI checks on this platform, documented in research/claude-code.md (found during page4) |
| `powershell.exe` invocation has ~7s of pure process-startup overhead on this dev machine (measured with a trivial `Write-Output` call — not specific to `Get-CimInstance`/`Get-Process`) | A blocking `ProcessDiscoveryService` call on every controller startup would add ~7-19s of real latency before the server could serve traffic | Found during page16: the `ProcessDiscoveryService` cross-check in `Reconciler` was decoupled from the blocking `reconcile()` path and runs in the background after the server starts listening (`runProcessDiscoveryCrossCheckInBackground`) — it's diagnostic-only and never drives session state, so this is safe. Measured real improvement: `startController()` now resolves in ~2.5s instead of ~19-22s. The root cause (why PowerShell itself is this slow on this machine — likely AV/execution-policy scanning) is unexplained and may not reproduce on other machines; the architectural fix (never block startup on a diagnostic-only check) is the right call regardless. |
| `ClaudeCodeAdapter`'s in-memory `sessions`/`projectPaths`/`listeners` maps (page8) grow by one entry per session started and are never evicted for the life of the daemon | Unbounded-looking memory growth over a genuine 24/7 run | Found during page21's bounded-memory audit. Not fixed with an eviction/LRU cache: every status (including terminal `COMPLETED`/`FAILED`/`STOPPED`) is legitimately resumable later per `SESSION_STATUS_TRANSITIONS`, and there is no session-deletion endpoint anywhere in the REST API today — evicting an entry risks a resumed session hitting `SessionNotFoundError` in the adapter while `SessionRepository` (SQLite, the real source of truth) still has it. For a single-user personal tool this is a working set that scales with how many sessions one person creates (realistically dozens to low hundreds over months), not an unbounded-per-request leak. Revisit if a session-deletion/archive endpoint is ever added — that would be the natural, safe eviction trigger. |
| `DISCOVERY_POLL_INTERVAL_MS` (`packages/config`) is defined but not read anywhere in `apps/controller/src` | Drift between persisted session state and reality between restarts is never caught — process discovery (page15/16) only ever runs once, at startup | Found during page21's bounded-memory audit while checking for stray intervals. Adding a recurring poller is new functionality, not a hardening fix, and the Phase 1 page sequence is otherwise closed — documented here as a known limitation and a natural Phase 2 candidate rather than built now. |
| A session marked `DISCONNECTED` by startup reconciliation (page16) currently has no way to actually be resumed | `POST /sessions/:id/resume` -> `SessionRegistry.resumeSession` -> `adapter.resumeSession(sessionId)` requires the adapter's own in-memory record of that session to still exist. Only `startSession` populates that record; a fresh `ClaudeCodeAdapter`/`FakeClaudeSessionAdapter` instance after a real restart has none, so `resumeSession` throws `SessionNotFoundError` for exactly the sessions reconciliation just marked `DISCONNECTED` — the one status `DISCONNECTED` is documented to transition *to* (`SESSION_STATUS_TRANSITIONS`: `DISCONNECTED -> STARTING`) doesn't actually work today | Found during pageB5's audit while designing a full HTTP-driven, two-instance Bordio recovery test — routed around it (the test instead exercises `bordio_links` recovery directly against two SQLite connections, not a full session-resume flow) rather than fixing it, since this is a pre-existing core session/adapter gap (page7-16), not Bordio-specific, and fixing it (the adapter needs a way to reconstruct its record from `SessionRepository` on a resume call) is real, scoped work for a dedicated future page — not silently left undiscovered, but deliberately not fixed inside a Bordio hardening pass. |
| pageB5's bounded-memory/backoff audit of `BordioApiClient`/`BordioNotificationService`/`BordioInboundPoller` | — | Confirmed clean: none hold per-session/per-task in-memory state that grows unboundedly (everything durable lives in SQLite via pageB2's repositories); confirmed `InProcessEventBus.publish()` never awaits a subscriber's async work, so `BordioApiClient`'s retry/backoff (up to ~3.5s) can't block a session dispatch or HTTP request. One real (non-memory) limitation found: `BordioInboundPoller.pollOnce()` doesn't follow `nextCursor`, so a poll tick only processes the first page of command-tagged tasks — self-correcting each tick (processed tasks get untagged and drop out of the filtered set) but throughput-bounded under a large backlog rather than broken. |
