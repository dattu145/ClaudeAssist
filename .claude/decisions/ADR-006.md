# ADR-006: Bordio integration is outbound-first, inbound is bounded polling (no webhooks exist)

## Status
Accepted

## Context
Bordio's REST API (`research/bordio.md`) has no webhooks — Bordio's own
docs call it "a placeholder for an upcoming feature" and recommend
polling with ETag-based conditional requests as the workaround. Rate
limits are real and enforced per key (120 GET/min, 60 write/min), and a
`304 Not Modified` still counts against the read quota. There is no
"updated since" filter on the tasks endpoint, so detecting inbound
changes requires fetching a filtered candidate set and diffing locally.

This project already has the two abstractions Bordio integration needs
to sit behind: `NotificationService` (page19, one interface, `Console`
is Phase 1's only implementation) and `CommandRouter`/`IntentResolver`
(page20, `Command` dispatch already decoupled from how a `Command` gets
produced).

## Decision
1. **Outbound is the primary, first-built direction.** A
   `BordioNotificationService implements NotificationService` mirrors
   notify-worthy session/task lifecycle events onto Bordio tasks —
   exactly the extension point ADR-002/page19 already exist for. Every
   Bordio task this integration creates is idempotency-keyed off the
   ClaudeOps entity it mirrors, so a crash-and-restart mid-sync can never
   double-create a Bordio task (research/bordio.md's idempotency
   section).
2. **Inbound is a bounded poller, not a webhook receiver — because
   Bordio has none.** A Bordio task tagged for ClaudeOps (a dedicated
   tag, e.g. `claudeops`) is polled on an interval, diffed against a
   locally persisted last-seen snapshot, and — when it carries a
   structured mapping to a session (via a custom field or task
   description convention, decided at implementation time, page-by-page
   per the Phase 2 roadmap) — translated directly into a `Command` and
   dispatched through the existing `CommandRouter`. This is deliberately
   **not** routed through `IntentResolver`: `IntentResolver` exists for
   free-text -> `Command` translation (voice, WhatsApp messages); a
   Bordio task's fields are already structured, so translating them is a
   plain mapping function, not an NLP concern in that interface's
   sense — using `IntentResolver` here would misuse the abstraction ADR-
   005 defined for a different problem.
3. **Both directions are optional, off by default**, gated by a new
   config var (`BORDIO_API_KEY` unset = integration disabled entirely),
   matching how every other Phase 1 feature with an external dependency
   (log rotation, the real `claude` CLI itself) defaults to off/absent
   rather than assumed.
4. **The Bordio API key is controller-side only, never in the mobile
   app** — this isn't a new rule, it's Bordio's own stated requirement
   ("server-side only") landing on the same rule `SECURITY.md` already
   has for every other secret in this project.

## Consequences
- No live/real-time sync in either direction is possible until Bordio
  ships webhooks — a documented limitation, not a design flaw in this
  project. Outbound updates land on the next `NotificationService.notify()`
  call (effectively real-time from ClaudeOps's side, since that's
  event-driven); inbound Bordio-initiated commands land on the next poll
  tick (bounded latency, not instant).
- `CommandRouter`'s design (page20: "proving the abstraction before
  voice ever needs it") pays off immediately — Bordio becomes the first
  real non-mobile `Command` source without any change to `CommandRouter`
  itself, exactly as ADR-005 intended.
- A new SQLite table/repository is needed to persist the ClaudeOps<->
  Bordio ID mapping and the inbound poller's last-seen snapshot — this
  is genuinely new state, not a repurposing of anything existing.
- Revisit direction #2's polling design entirely if Bordio ever ships
  webhooks — that would let inbound become event-driven and the poller
  could be deleted, not reworked (it sits behind the same `CommandRouter`
  boundary either way).
